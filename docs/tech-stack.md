# 技术选型

| 领域 | 选型 | 使用阶段及考虑 |
|---|---|---|
| 语言与基础环境 | Windows、VS Code、Python 3.12 | Phase 1 声明兼容范围、建立运行入口和可复现的开发环境。优先复用现有虚拟环境。 |
| 本地推理 | Ollama、`qwen3.5:4b` | Phase 2 实测多轮、流式、结构化输出和工具调用。Phase 3 封装模型接口，保留更换模型的能力。 |
| Agent 核心 | 原生 Python、自研 Agent Loop | Phase 4 至 Phase 7 逐步建立调用协议、工具分发、执行循环和任务规划。框架对比安排在核心机制可演示之后。 |
| 持久化 | SQLite、Python `sqlite3` | Phase 8 保存任务、事件和检查点。本地运行可以直接管理单个数据库文件。 |
| 文档读取 | PyMuPDF、Python 文本 I/O | Phase 9 提取数字 PDF 文本并保留页码，读取 TXT 和 Markdown。扫描件能力视样本需求再评估。 |
| 向量检索 | 本地嵌入、FAISS | Phase 9 验证 Windows 和 Python 3.12 安装兼容性，按样本选择嵌入模型和索引，记录检索质量与内存。 |
| 搜索 | 可替换的提供方接口 | Phase 5 定义请求、结果、配额和错误契约。真实服务按覆盖范围、费用与可用性选择，在 Phase 10 验证研究链路。 |
| 评估 | Python 测试与固定样例 | Phase 3 起按模块测试，Phase 11 建立统一指标和评估入口。 |
| 用户界面与 API | Streamlit、FastAPI | Phase 13 接入。界面与 API 调用同一研究工作流。 |
| 版本管理 | Git、GitHub | Phase 0 初始化本地仓库，Phase 1 完成版本管理配置，Phase 14 整理 GitHub 交付。 |

## 本地资源策略

- 以 8 GB 显存和 16 GB 内存为基准。模型、上下文、输出长度、文档块大小、检索条数和并发数采用可调设置，默认值根据真实任务测量确定。
- 每次调用只传入当前问题所需的对话、工具结果和相关证据。将完整历史和中间结果保存在任务存储中，长文按块处理。
- 模型推理和文档嵌入分别测量。在显存压力较大时优先串行执行，记录延迟、峰值资源和效果。
- 默认推理走本地 Ollama。联网检索由明确配置的提供方完成，记录超时和配额错误。本地文档研究可独立验证。
- 项目依赖按阶段引入。LangChain、CrewAI、AutoGen 等框架的使用由后续对比实验决定。
